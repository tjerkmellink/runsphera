# Roadmap

Living priority list for RunSphera. **Done** is the build-up record; everything below it is what's next, themed and roughly ordered by impact. Keep the user-visible payoff at the front of each item — the bullet should explain *why* the feature exists, not just *what* it is.

## Bugs to chase

*Seventeen failure paths fixed — sixteen from five rounds of independent review (2026-10-23 and 2026-10-24), one from manual testing; kept here as the record of what was wrong.*

- ✅ **Moving a workout into the next week made it disappear** — `move_workout` updated `planned_date` and `day_of_week` but not `week_number`, and `get_plan_weeks` groups by `week_number`. Sunday's long run moved to Monday stayed filed under the previous week, which renders behind the "Show N previous weeks" collapse once elapsed — so it looked gone. The swap case mis-filed both rows, leaving one week spanning eight days with two Mondays and the next with two Sundays. Both rows now re-file into the week containing their new date, via `_week_for_date()`. **Found by manual testing, not by any review round** — it needed someone to move a workout and look at the page. See [architecture.md](architecture.md) → "`week_number` must agree with `planned_date`".

- ✅ **An offline edit made a stale prescription permanent** — the worst of the series, and an interaction between two earlier fixes rather than a single bug. Round 2 kept `garmin_workout_id` when a Garmin delete failed, so a retry had a handle; round 4 made a fully-pushed row a push no-op. Together: edit a pushed workout with Garmin unreachable, keep both columns, and *every* later push returned early — the watch held the pre-edit prescription forever while the UI showed the new one as on-watch. Fixed by making the three states representable in the two existing columns: keep the id, drop `pushed_at`. No migration needed, and it routes the next push through the stranded-upload path already built in round 3.
- ✅ **Event swaps discarded Garmin ids before confirming deletion** — `apply_swap` and `revert_swap` both cleared `garmin_workout_id`/`pushed_at` and committed *before* attempting the delete, which never happened at all without a client. The swap snapshots don't carry ids, so neither revert nor cleanup could recover them, and a displaced long run could stay scheduled on what was now a rest day. Both now release first and clear only what Garmin confirmed. `event_swap.py` was missed by the round-4 audit because that audit grepped a list of files rather than the package.
- ✅ **Editing repetitions silently demoted them to I pace** — `_zone_for_workout` reads R vs I off the title token, and `_derive_title` re-derived a generic "Intervals N×M m" on save. A VDOT-50 6×400 m repetition session recalibrated from R (232 s/km) to I (250 s/km) with no VDOT change. The noun now comes from the step's own `zone` tag, which is the authority; "Strides" keeps its identity too.
- ✅ **Concurrent pushes uploaded duplicates** — "Push week" and an individual Push run on different threads of one process; both could read a row as unpushed, both upload and schedule, and the second write overwrote the first id, orphaning that copy. Pushes are now serialised per row via `push_lock()` with state re-read inside the lock.

- ✅ **The unpush route overrode its own helper** — `unpush_session` was fixed in round 3 to keep push state on a failed delete, and the route above it cleared that state itself in two branches (the exception path and the no-client path), ignored the helper's return value, and flashed "Removed from your watch." regardless. The helper fix was invisible to the runner. The route now honours the result and says what actually happened; the decision is extracted as `unpush_outcome()` so it is testable without a request.
- ✅ **Turning strength off stranded pushed sessions and erased today's completed one** — `clear_future_sessions` ran an unconditional `DELETE ... WHERE planned_date >= today`, discarding `garmin_workout_id` with no Garmin call, so sessions stayed scheduled on the watch with nothing pointing at them and re-enabling pushed a duplicate onto the same day. The same predicate deleted a session *completed that morning*, against the docstring's promise to keep history. It now takes a client, releases pushed copies first, keeps anything Garmin refuses, never deletes a completed session, and reports counts so both callers (the toggle route and `reshape_plan`) can surface them.
- ✅ **Replaying a successful push uploaded a duplicate** — the round-3 guard only covered stranded uploads (`id` set, `pushed_at` NULL). A fully-pushed row fell through to a second upload and overwrote the id, orphaning the first copy. Pushing an already-pushed workout is now a no-op that returns the existing row.

- ✅ **Interval sessions understated weekly volume** — quality rows carried the *budget* distance (`q1_km`) while `_interval_structure` built Daniels' published rep counts inside a fixed 2 km warm-up and cool-down. A 5 km headline prescribed ~10.7 km, so every interval week reported less than it asked for, and `distance × headline pace` then billed the whole session at I pace. Headlines are now derived from the structure at generation time, the same way an edit already derived them. Fixed rather than trimmed: shrinking reps to fit a mileage figure would change a published training number to protect a display one. See [garmin-workout-push.md](garmin-workout-push.md) and [test_volume_truth.py](../tests/test_volume_truth.py).
- ✅ **Half-marathon peak long run never delivered its T-pace finish** — the description promised "5 km @ ~T pace" but the branch returned no structure, so the watch received one flat E-pace step for the whole 19 km. Now returns easy + T + cool-down steps with zone tags, matching the marathon-goal sibling directly above it.
- ✅ **Strength unpush reported success after a failed delete** — `unpush_session` swallowed the error, cleared `garmin_workout_id`/`pushed_at` and returned `True`, so the modal said "Removed from your watch." for a session still on it, with no handle left to retry. `push_session` likewise uploaded a replacement after failing to delete the prior copy. Both now go through `release_garmin_copy()`; the push refuses loudly rather than stacking a second copy on the same day.

- ✅ **Race day inherited the replaced session's structured steps** — the Daniels race overlay set type, title and targets on whichever day the race landed on, but left `workout_structure` intact. `planned_to_garmin_workout` prefers any structure it finds over the headline distance and never gates that on the type, so a Thursday 10 km race pushed warm-up + 6×100 m R-pace strides + cool-down to the watch under a "Race day" title. Reproduced, then fixed by clearing the structure in the overlay. Pfitzinger, Higdon and C25K already did this; Daniels was the only gap. Pinned by [test_race_overlay_structure.py](../tests/test_race_overlay_structure.py).
- ✅ **Reshaping a pushed workout threw away the retry handle** — `edit_workout`, `move_workout`, `apply_workout_swap`, `recalibrate_paces` and `reshape_plan` all cleared `garmin_workout_id`/`pushed_at` and committed *before* attempting the Garmin delete, and `edit_workout` then uploaded a replacement even when the delete had failed. With `client=None` (auth gone) the old workout stayed on the watch with no id left to retry. Now all five go through `release_garmin_copy()` and clear only on a confirmed delete; failures surface as banners instead of being discarded. See [garmin-workout-push.md](garmin-workout-push.md).
- ✅ **A failed schedule stranded an uploaded running workout** — `push_workout_to_garmin` persisted the id only *after* `schedule_workout` succeeded, so a scheduling error left a copy on Garmin that the app knew nothing about, and every retry uploaded another. The id is now recorded the moment the upload lands, `pushed_at` waits for the confirmed schedule, and a stranded copy is released before the next attempt.

- ✅ **Cross-origin requests could delete a plan** — the app has no login, and loopback binding does not stop a form on another site POSTing to `http://localhost:8000/plans/3/delete`. Plan ids are sequential, and plans are not regenerable. Fixed with a `Host` allow-list plus an `Origin`/`Referer` match on state-changing methods, covering all 70 POST routes through one middleware. See [same-origin-protection.md](same-origin-protection.md).
- ✅ **Failed Garmin cleanup threw away the retry handle** — `cleanup_pushed_workouts` cleared `garmin_workout_id` and `pushed_at` even when `delete_workout` raised, leaving the workout on the watch with no id left to retry and making a later re-push duplicate rather than replace. Push state is now cleared only for deletions Garmin confirmed, and the failure count reaches the runner as a banner instead of being discarded by the caller.
- ✅ **Strength sessions reported success after a failed schedule** — upload and scheduling are separate Garmin gates, but a scheduling failure was logged and then stamped `pushed_at` anyway, so the modal said "Pushed to your watch." for a session that never reached the calendar. `garmin_workout_id` is now recorded on upload (so a retry replaces rather than duplicates) while `pushed_at` waits for a confirmed schedule, and the modal says what actually happened.

## Road to 1.0 — versioning, install & release

The work to turn this from "runs on my machine" into a versioned **1.0** that can tell itself when it's out of date. Decisions locked: **git-clone + bootstrap-script** install, and a **detect-and-notify** update channel (the app spots a new release and tells you; you run the pull). Tiers are priority order — finish a tier before starting the next.

### Tier 1 — Ship 1.0

The minimum to call something "1.0" and tag it.

1. **Single-source version** — `runsphera/__init__.py` → `__version__ = "1.0.0"` (SemVer). Surface it in the nav footer + Settings so you always know what's running. Everything else keys off this string.
2. **Release branch + tag model** — `main` = development; a **`stable`** branch always points at the latest released tag (`v1.0.0`, `v1.1.0`, …). Tags are the real release markers, `stable` is the channel the app tracks. Document the "cut a release" steps (bump `__version__` → tag → fast-forward `stable`).
3. **CHANGELOG.md** — Keep-a-Changelog format, seeded with everything shipped so far as `1.0.0`. Each future tag gets an entry.
4. **Cross-platform install + bootstrap script** — README install is Windows-only (`.venv\Scripts\…`) today; add macOS/Linux paths and an `install.ps1` / `install.sh` that creates the venv, installs deps, and launches in one step.
5. **Pin / lock dependencies** — `requirements.txt` uses `>=` ranges (reproducibility risk for a release). Pin to known-good versions; split dev-only tools (`pytest`, `ruff`) into `requirements-dev.txt` (neither is currently declared).

### Tier 2 — In-app update channel (detect + notify)

Make the running app aware of its own staleness.

6. **Version-check service** — compare local `__version__` against the newest release on the remote. Git-based (`git ls-remote --tags`, or a `VERSION` file on `stable`) so it works against any remote, public or private. Cache the check (once/day) so it's not a per-load network hit.
7. **"Update available" banner** — a dismissible Settings (and maybe dashboard) banner: *"v1.1.0 available — you're on v1.0.0"* linking to the CHANGELOG + the one-line `git pull` upgrade command. Notify only; no auto-pull.
8. **Verify the upgrade path** — confirm `db.connect()`'s idempotent migrations run on the new version's first launch (they should — just prove it and document "what happens when you update"). This is what makes a pull-to-update safe.

### Tier 3 — Public-repo readiness

The public repo is published from a clean, single-commit snapshot, so there is no legacy history to audit. What remains is making the front door presentable.

9. ✅ **Clean public history** — *resolved by construction.* The public repo is seeded from a single snapshot commit rather than filtered from a longer history, so no prior commit can leak a credential. Keep it that way: secrets belong in `.env` or the local SQLite, never in a tracked file. `data/*.db`, `.env`, `.garmin_tokens/` and `data/desktop.log` are all gitignored.
10. ✅ **LICENSE + disclaimer** — *done.* MIT `LICENSE` at the repo root, plus README **License** and **Disclaimer** sections: not affiliated with Garmin or Anthropic, `garminconnect` is unofficial and may fall outside Garmin's ToS, training output is not medical advice, no warranty + back up the non-regenerable tables. (Supersedes the old "Open-source polish" parked item.)
11. **GitHub-ready README pass** — screenshots / a short GIF, version + license badges, optional `CONTRIBUTING.md` + issue templates if accepting contributions.

### Tier 4 — Nice-to-have / later

12. **`pyproject.toml` + console entry point** — `pip install .` then a `running-coach` command instead of `python -m runsphera.web`. Cleanest Python-native install; enables an eventual PyPI publish.
13. **Docker + compose** — one `docker compose up`, `data/` as a volume, keys via env. The "just works for non-Python users" headline path if the project ever goes wide.
14. **CI (GitHub Actions)** — run `pytest` + `ruff` + a template-parse check on every push. Catches regressions the manual smoke tests miss.
15. **One-click / background auto-update** — upgrade the Tier-2 notify into an in-app button (or silent channel) that runs `git pull` + migrations + restart. Deferred deliberately: surprise restarts and rollback need care, and notify-only covers the 1.0 need.

- **Course / map per run** — Garmin returns GPX; show the route in the run detail modal. Pure visual reward.

- **Pre/post-run food tips** — use the calorie burn from recent activities (`activities.calories` already comes back from Garmin) to estimate today's expenditure and suggest nutrition. Shown beside the Today's workout card.

Nothing changed about what the runner was asked to run — the number just stopped lying. But `_allocate_week` sizes easy mileage against a budget the quality session then blows through, so the *easy* allocation should shrink to absorb a structured session's real cost. Deliberately not fixed alongside the reporting bug: it changes prescriptions, not reports, and wants its own decision. Pin any change to Daniels' published volume guidance, not to current output.
- **Target-time sanity check** against current VDOT predictions — when creating a plan, flag a target time that's unrealistic for the current fitness ("your VDOT predicts 1:48 for a half; your goal of 1:35 implies +12 VDOT points in N weeks, which is aggressive").

### Fun, small
